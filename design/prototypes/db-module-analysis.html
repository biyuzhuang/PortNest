A方案 A · 纵向切分：服务层 + 页签控制器

保留现有组件树、视觉与交互，只把"谁干什么"摆正。核心是引入一层不依赖 Solid 的纯 TypeScript 服务，再用一组按页签类型划分的控制器把服务与状态接起来，容器组件退回布局角色。

图 2　方案 A：视图 → 控制器 → 服务 → 传输，四层单向依赖；状态按关注点分片，控制器只做"接线"。

模块分层与职责

  • 视图：只做渲染与事件上抛，不再出现 api.、不再自己推导选中项。
  • 控制器：一类页签一个工厂，持有该页签的生命周期逻辑（加载、失效、竞态、错误槽），对外只暴露 props 与 actions。
  • 服务：函数式，(ctx, args) => Promise；ctx 只含 connectionId / protocol。不感知 UI。
  • 传输：仅 IPC 映射与类型。

依赖关系

  • 严格单向：视图 → 控制器 → 服务 → 传输。
  • 控制器可读写 store；服务不碰 store（保证可单测）。
  • 控制器之间不互相调用，跨页签影响走 metadata.invalidate() 这类显式事件。
  • 禁止子面板直连 api —— 由 lint 规则或约定守住。

主要改动范围

  • 新增 src/services/database/{metadata,rows,designer,transfer,query,schema}.ts
  • 新增 src/workspace/database/{useMetadata,useTabs,useTableTab,useQueryTab,useTransfer,useSelection,useDialogs}.ts
  • 新增 src/stores/database/{metadataStore,tabsStore,viewStore,requestScope}.ts，原 databaseWorkspaceStore 拆分后删除
  • 重写 DatabaseWorkspace.tsx（1162 → 约 200 行）；ObjectPanel / QueryPanel 去掉 api 调用并改用 props
  • TableTab 瘦身：只留"属于这个页签的事实"，UI 态与草稿分到 tabsStore.tableUi[tabId] / drafts[tabId]
  • 持久化收敛到 preferences，带 schemaVersion + 迁移函数（8 个键统一接管）

优点

  • 职责边界立刻清晰，新增"一段视图/一类页签"不需要动容器
  • 服务层可脱离 UI 单测（当前几乎无法测）
  • 界面零改版，可分批合入，每批都能独立验证
  • 为方案 B 打底：控制器就是未来 feature 的雏形

缺点 / 风险

  • 文件数从 22 增至约 40，初期跳转成本上升
  • 状态拆分会触及所有 patchTab 调用点（约 40 处），需要一次通改
  • 需要写数据迁移，否则用户列宽/历史/展开态会丢

适用场景：想把模块做"稳"，后续半年内还要持续加功能（更多协议、更多对象类型、更多导入格式），但不想改视觉。

B方案 B · 横向分层：工作台内核 + 可注册的 Feature

把数据库模块当成一个"小应用"来组织：core 提供连接、能力矩阵、请求总线、只读与权限；feature 各自成套（状态切片 + 视图 + 命令）；registry 把"页签类型"映射到 feature，容器只负责遍历注册表。

图 3　方案 B：按"功能"纵向成块，容器与 feature 通过注册表解耦；协议差异收进能力矩阵。

模块分层与职责

  • Shell：布局 + 按注册表渲染，不含任何业务分支。
  • Feature：自己的状态切片、视图、命令；对内自治，对外只暴露命令。
  • Core：连接、能力、请求总线、策略、偏好。
  • Registry：tab.kind → feature；也是"能力→菜单项"的唯一开关点。

数据流

  • 命令总线：dispatch("table.applyChanges")，返回结果与错误槽。
  • 状态按 feature 切片，跨 feature 读取走 core 的只读选择器。
  • 右键菜单由 registry 依据能力矩阵生成，不再在容器里写死一堆 if。

主要改动范围

  • 新增 src/features/database/{browse,table,query,design,transfer}/，每个含 slice.ts / View.tsx / commands.ts
  • 新增 src/core/database/{connection,capabilities,request,policy,preferences}.ts 与 registry.ts
  • 删除 databaseWorkspaceStore.ts 与 DatabaseWorkspace 的全部业务逻辑（后者只留布局）
  • 右键菜单、工具条按钮改为"能力声明"驱动，视觉上需要重新校对（菜单项顺序/禁用态可能变化）

优点

  • 扩展性最好：新协议只加 capability，新页签只加 feature
  • 天然支持"功能裁剪"（某协议不支持设计器时直接不注册）
  • 模块边界可机械校验（feature 之间禁止 import）

缺点 / 风险

  • 改动面最大：几乎重写，回归测试成本高
  • 注册表 + 命令总线是新的抽象，团队需要适应期
  • 当前只有 3 种页签、3 种协议，收益暂时小于成本

适用场景：确定要长期演进成"多协议数据库工作台"（PG / HighGo / Redis / Mongo 各自能力差异大），或要做插件化、多窗口。

C方案 C · 最小侵入：只修边界，不搬文件

不调整目录结构，只做三件"止血"的事：把 IPC 调用集中到一个服务文件、把 TableTab 里的 UI 态拆出去、让子面板不再直连 api。目标是用最小风险消掉 P1 问题。

图 4　方案 C：只加一层薄服务并搬走一部分状态，结构其余部分保持原样。

优点

  • 改动小、可 2–3 天完成，回归面窄，界面零变化
  • 立刻解决"三条请求路径、反馈不一致"这个最影响体验的问题
  • 数据迁移可控（只动列宽/分页一类 UI 态）

缺点 / 风险

  • 1162 行容器仍在，后续加功能继续变胖
  • 服务文件会变成新的"大杂烩"，只是换了个位置
  • P1 的"状态副本 / 三套选中"没有解决，问题会复发

适用场景：近期有发版压力，只想先稳一稳；或作为方案 A 的第一阶段。

6需要你先确认的取舍

下面 8 项会直接改变实施方式，麻烦按编号回复（例如 1B / 2A / 3A），或直接说"按推荐来"。

01
选哪版方案？

A 纵向切分（推荐，界面零变化）　B Feature 化（重写）　C 最小侵入（止血）　D 先 C 再 A（推荐路径）

02
重构期间能否接受界面"零变化"作为硬约束？

若可以，方案 A 的每一步都能用现有截图做像素级回归；若允许顺手改交互（例如把三处表信息合并成一处），能顺带消掉一个 P1。

A 零变化　B 允许合并信息面板　C 允许调整工具栏/菜单

03
TableTab 里的 UI 态（页码/排序/筛选/列宽/当前段）要不要挪出去？

挪出去：标签数据更"纯"，但切标签时要按 tabId 回填；不挪：改动小，但 24 字段的类型会继续膨胀。

A 挪到 tableViewStore　B 留在 TableTab，只做字段分组

04
错误与 loading 要怎么呈现？

现在是一条全局错误串 + 一个全局 loading 计数，后一次失败会覆盖前一次，任意请求都让整棵树显示"正在加载"。

A 每个页签/资源独立错误槽（页签内联）　B 全局 toast + 保留顶部错误条　C 维持现状，只按资源分 loading

05
是否要支持多个标签同时执行 SQL？

现在是单个 runningTabId，在 A 页签运行时会点亮 B 页签的按钮状态。改成集合可以并行，但"停止"要指定目标。

A 改为 Set<tabId>，支持并行　B 保持单任务（更简单，符合"一个连接一个会话"）

06
历史数据要不要迁移？

涉及 8 个 localStorage 键（列宽、冻结列、查询历史、收藏、编辑器高度、树宽、只读、偏好）。不迁移的话，用户升级后列宽和历史会"回到默认"。

A 写迁移函数 + 版本号（推荐）　B 不迁移，接受重置　C 只迁移查询历史与列宽

07
对象列表的搜索/排序，保持前端还是走后端？

现在对象列表在前端过滤排序（10 列比较器），表数据走后端。库很大（几千张表）时前端方案会卡。

A 保持前端（实现简单）　B 统一走后端分页（需要后端加接口）

08
api.ts 里的 mysql_* / postgres_* 旧命令要不要一并清掉？

UI 已全部走 database_*，这两套是历史遗留；清理可减小类型面，但需确认没有外部脚本/测试在调用。

A 一并清理（含 Rust 侧命令）　B 只删前端封装，Rust 命令保留　C 暂不动
